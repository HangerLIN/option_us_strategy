# 回测收益计算修复计划

## 一、问题分析

### 1.1 当前实现的问题

通过代码审查发现，回测系统在 **equity track 模式** 中使用了**固定时间窗口**来计算收益，这与文档要求不符：

**问题代码位置：** `apps/backtest/bt_runner.py`

```python
# 第205行：定义固定时间窗口
horizons = (5, 15, 30, 60)

# 第319行：为每个BUY信号计算固定窗口收益
returns = _compute_horizon_returns(frame, ts_utc, entry_price, horizons)

# 第532-547行：计算固定时间窗口收益的函数
def _compute_horizon_returns(
    frame: pd.DataFrame,
    ts_utc: datetime,
    entry_price: Decimal,
    horizons: Sequence[int],
) -> Dict[int, Decimal | None]:
    results: Dict[int, Decimal | None] = {}
    for minutes in horizons:
        future_ts = ts_utc + timedelta(minutes=minutes)
        bar = _lookup_bar(frame, future_ts)
        # ... 计算 5/15/30/60 分钟后的收益
    return results
```

**生成的错误指标：**
- `RET_SIG_{signal_code}_5M`
- `RET_SIG_{signal_code}_15M`
- `RET_SIG_{signal_code}_30M`
- `RET_SIG_{signal_code}_60M`

### 1.2 文档要求

查阅所有文档（`docs/` 文件夹下所有文件），**没有任何地方提到按固定时间窗口计算收益**：

1. **交易信号生成与组合构建.md**：只描述买入和卖出信号的生成规则
2. **回测与绩效评估开发文档.md**：
   - 第102行 `bt_trades` 表包含 `open_ts, close_ts, open_px, close_px, pnl`
   - 强调"可审计交易明细"与"分策略绩效"
   - 没有提及固定时间窗口
3. **执行与成本控制开发文档.md**：只描述订单执行逻辑
4. **数据管道与预处理开发文档.md**：只描述数据获取和指标计算

**正确的收益计算逻辑应该是：**
- 每个正股 symbol 的相邻 BUY 信号 → SELL 信号之间的收益
- 即：开仓价格 → 平仓价格之间的实际收益

### 1.3 当前代码中的正确部分

代码中已经存在正确的收益计算逻辑（TFE - Time From Entry）：

**`apps/backtest/bt_runner.py` 第265-293行：**
```python
open_entries: List[Dict[str, Decimal]] = []

for event in signals:
    if event.side == SignalSide.SELL:
        # 卖出信号：计算所有未平仓的收益
        exit_bar = _lookup_bar(frame, ts_utc)
        if exit_bar is not None:
            exit_price = Decimal(str(exit_bar["close"]))
            for entry in open_entries:
                tfe_ret = (exit_price - entry["entry_price"]) / entry["entry_price"]
                accumulator.add_tfe(entry["signal_code"], tfe_ret)
            open_entries.clear()
    
    if event.side == SignalSide.BUY and accepted:
        # 买入信号：记录开仓
        open_entries.append(
            {"signal_code": event.signal_code, "entry_price": entry_price}
        )
```

**生成的正确指标：**
- `RET_SIG_{signal_code}_TFE_MEAN` - 平均收益
- `RET_SIG_{signal_code}_TFE_P50` - 中位数收益
- `RET_SIG_{signal_code}_TFE_P90` - 90分位收益

## 二、修复方案

### 2.1 核心原则

1. **移除所有固定时间窗口的收益计算逻辑**
2. **只保留基于信号对（BUY → SELL）的收益计算**
3. **确保 option track 模式和 equity track 模式逻辑一致**

### 2.3 Option Track 模式验证

**需要确认的点：**

`apps/backtest/strategy/option_signal_strategy.py` 使用 Backtrader 框架：
- 通过 `notify_order` 方法记录每笔交易（第340-374行）
- 记录到 `bt_trades` 表，包含 `side`, `quantity`, `price`, `trade_ts`
- Backtrader 的 `notify_trade` 会自动配对开仓和平仓，计算 PnL

**验证结论：** Option track 模式已经是正确的，因为：
1. 它基于实际的交易配对（买入订单 + 卖出订单）
2. PnL 由 Backtrader 框架自动计算（买入价 vs 卖出价）
3. 没有使用固定时间窗口

**无需修改 option track 模式。**

## 四、风险评估

### 4.1 影响范围

- **核心影响：** equity track 模式的收益计算逻辑
- **次要影响：** 
  - 历史回测报告中的指标会发生变化
  - 依赖固定窗口指标的分析脚本需要更新

### 4.2 兼容性

- **向后兼容性：** 不兼容
  - 旧的回测数据包含 `*_5M/*_15M/*_30M/*_60M` 指标
  - 新的回测数据只包含 `*_TFE_*` 指标
  
- **建议：** 
  - 在 `bt_runs` 表的 `parameters` 字段中添加版本标记
  - 例如：`{"calculation_version": "v2_signal_pairs"}`

### 4.3 回滚方案

如果修改后发现严重问题：

1. **代码回滚：**
   ```bash
   git revert <commit_hash>
   git push
   ```

2. **数据库回滚：** 无需特殊操作（保留历史数据）
